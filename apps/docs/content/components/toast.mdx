## Overview

Toast notifications are lightweight, ephemeral messages that appear at the
bottom of the viewport to confirm actions, surface errors, or communicate
system events. They auto-dismiss after a set duration, allowing the user to
continue their workflow without interruption. Toasts stack vertically and
animate smoothly. Long-lived messages belong in inline alerts instead.

### Use cases

- **Action confirmation:** Confirm that a save, update, or deletion completed
  successfully (e.g. "Client profile updated").
- **Undo opportunity:** Provide a brief window to reverse a destructive or
  important action before it becomes permanent (e.g. "Session deleted" with an
  Undo button).
- **Error feedback:** Notify the user of a failed operation that does not
  require a page-level alert (e.g. "Payment could not be processed").
- **System event:** Surface asynchronous events the user should be aware of
  but does not need to act on immediately (e.g. "Import complete").

<Callout type="info" title="Imperative API">
  In real applications you typically call the imperative `toast()` and
  `dismissToast()` helpers from `@bsport/kaizen-primitive-core`. They render
  through a `ToastManager` mounted near the app root. The static `Toast`
  component below is what `ToastManager` paints under the hood.
</Callout>

### Best practices

#### General

<DoDont>
  <Do caption="Keep toast copy under two short lines — title plus one sentence description." />
  <Dont caption="Use a toast for information that requires user input or a multi-step decision — use a Modal instead." />
  <Dont caption="Use a toast for persistent page-level warnings or errors — use an Alert instead." />
</DoDont>

<Callout type="warning" title="Caution">

- `duration: 0` (indefinite) can clutter the viewport — reserve it for cases where the user must acknowledge the content.
- Always provide a `title` or `description` alongside an icon; iconographic meaning varies across contexts.

</Callout>

#### Status

<DoDont>
  <Do caption='Use status="default" for neutral and confirmatory feedback alike ("Changes saved", "Link copied").' />
  <Do caption='Use status="critical" to surface operation failures or validation-blocking errors.' />
  <Dont caption="Overload a single toast with multiple messages — one action, one toast." />
</DoDont>

<Callout type="info" title="positive status">
  A `positive` variant exists in the codebase but is not currently in use. All
  success confirmations use `default`. If a dedicated success style is needed in
  the future, `positive` can be enabled without code changes.
</Callout>

### Behavior

#### Dismissal

Toasts auto-dismiss after `duration` milliseconds (default 5 000 ms). Setting
`duration` to `0` disables auto-dismissal; the toast persists until dismissed
programmatically via `dismissToast(id)` or via the action button. Dismissal
plays a 300 ms fade-out animation before removal from the DOM.

#### Action button

When `buttonLabel` is provided, a small solid `Button` (`kind="default"`,
`size="sm"`) is rendered. Clicking it fires `onButtonClick` and then
automatically calls `onDismiss`. When only `buttonIcon` is provided, an
icon-button (`kind="icon-button"`, `intent="flat"`, `color="onstrong"`) is
rendered instead.

#### Persistence

Use `duration: 0` only for toasts that require explicit user acknowledgement
(e.g. "Your session is about to expire — extend?"). In all other cases, rely
on the default auto-dismiss behaviour.

#### Stacking and animation

Toasts stack from the bottom of the viewport. On hover, the group fans out
(`translateY: -88px` per item) and all toasts scale to `1`. When not hovered,
stacked toasts compress (`translateY: -14px`) and shrink by `0.05` per stack
position. A maximum of 3 toasts render at a time; additional toasts are
invisible and non-interactive.

#### Responsiveness

The toast container is positioned `fixed`, centred horizontally
(`left-1/2 -translate-x-1/2`), and sized at 75% of the viewport width with a
`max-width` of `600px`.

### Edge cases

- **Multiple simultaneous toasts** — `ToastManager` stacks up to 3 visible
  toasts. Older toasts beyond this limit are hidden with `opacity-transparent`
  and `pointer-events-none`.
- **Very short duration** — If `duration` is set below `1000`, a console
  warning is emitted: durations this short are unlikely to be readable.
- **No title and no description** — The toast renders an empty content area.
  Always provide at least one of them.
- **Toast triggered before manager mount** — The imperative `toast()` function
  lazily creates the `ToastManager` portal if it doesn't exist yet, with a
  10 ms delay for initialisation.
- **Programmatic dismissal** — Use `dismissToast(toastId)`, passing the ID
  returned by the `toast()` call.
