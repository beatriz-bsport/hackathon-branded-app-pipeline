## Overview

Toast is a short, non-blocking message fixed to the bottom of the viewport. It
confirms an action, surfaces an error, or reports a system event — then
auto-dismisses so the user can continue without interruption. Toasts stack and
animate as a group; persistent page-level warnings belong in
[Alert](/components/alert) instead.

### Use cases

- **Action confirmation** — confirm a save or update when the outcome is not
  fully visible (e.g. "Client profile updated", settings synced on another tab).
  Prefer toast over a positive [Alert](/components/alert) for these brief
  acknowledgments — see **Alert vs Toast for success** on the Alert page.
- **Undo window** — offer a brief Undo after a destructive action (e.g.
  "Session deleted" with an Undo button).
- **Operation failure** — notify when an API call fails but a page-level alert
  is unnecessary (e.g. "Could not copy link").
- **Async completion** — report background work the user triggered (e.g.
  "Export ready — download started").
- **Clipboard feedback** — confirm copy-to-clipboard with a title-only toast.

<Callout type="info" title="Imperative API">
  In applications, call `toast()` and `dismissToast()` from
  `@bsport/kaizen-primitive-core`. They render through a `ToastManager` portal
  mounted on `document.body`. The static `Toast` component is what the manager
  paints for each item.
</Callout>

For when toast is the right confirmation pattern, see
[Confirmation](/patterns/confirmation).

## Guidelines

- **Keep it brief** — one action, one toast; title plus at most one sentence of
  description.
- **Transient by default** — rely on the 5 s auto-dismiss unless the user must
  explicitly acknowledge the message.
- **Not for blocking state** — errors that halt the workflow belong in
  [Alert](/components/alert) or inline field validation.
- **One outcome per toast** — fire a new toast per action; do not batch unrelated
  messages.
- **Icon reinforces, not replaces** — always pair icons with a `title` or
  `description`.

### Best practices

#### General

<DoDont>
  <Do caption="Confirm saves and deletes with a toast when the result is off-screen or not obvious from the UI." />
  <Do caption="Front-load the meaningful word in the title so users scanning the stack grasp the outcome quickly." />
  <Do caption="Use buttonLabel for Undo or a single recovery action that fits in one short label." />
  <Dont caption="Long explanations and multi-option choices belong in a Modal, not a toast." />
  <Dont caption="Unrelated outcomes deserve separate toasts or product-level consolidation, not one overloaded message." />
  <Dont caption="Persistent warnings that stay until resolved belong in Alert, not toast." />
</DoDont>

<Callout type="warning" title="Caution">

Setting `duration: 0` keeps a toast until dismissed programmatically or via its
action button. Reserve indefinite toasts for cases that need explicit
acknowledgement — otherwise the stack clutters the viewport.

</Callout>

#### default status

<DoDont>
  <Do caption='Use status="default" for neutral confirmations and success feedback alike ("Changes saved", "Link copied").' />
  <Dont caption="Default toasts with multiple sentences bury the outcome — move detail to an alert or modal." />
</DoDont>

#### critical status

<DoDont>
  <Do caption='Use status="critical" for operation failures or errors that block the immediate goal.' />
  <Dont caption="Routine success reads fine on default — critical is for failures that block the goal." />
</DoDont>

<Callout type="info" title="positive status">
  A `positive` variant exists in the API but is not used in product today. All
  success confirmations use `default`. Enable `positive` later without API
  changes if a dedicated success style is needed.
</Callout>

### Content rules

Write in present tense, second person. Keep titles under one line; descriptions
to a single supporting sentence.

**Success**

> Changes saved

> Your payout settings have been updated.

**Failure**

> Could not save

> Check your connection and try again.

**Undo**

> Session deleted

> Undo

### Behaviors

#### Dismissal

Toasts auto-dismiss after `duration` milliseconds (default 5 000). `duration: 0`
keeps the toast until `dismissToast(id)` or the action button fires. Exit uses a
300 ms animation before DOM removal.

#### Action button

`buttonLabel` renders a small solid Button; `buttonIcon` alone renders an
icon-button. Both call `onButtonClick` then `onDismiss`. The action is not a
separate persistent control — it always closes the toast.

#### Persistence

Toasts are ephemeral. They do not survive full page navigation unless your app
re-fires them. Use `duration: 0` only when explicit acknowledgement is required.

#### Stacking and animation

`ToastManager` stacks up to three visible toasts from the bottom center. On
hover, the group expands (`translateY: -88px` per item, scale 1); when not
hovered, items compress (`translateY: -14px`, scale down 0.05 per level). Toasts
beyond the third are invisible and non-interactive until earlier ones dismiss.

#### Responsiveness

The manager container is `fixed`, horizontally centred, 75% viewport width with
`max-width: 600px`.

### Edge cases

- **Multiple simultaneous toasts** — only three render visibly; older items wait
  behind the stack.
- **Very short duration** — values under 1000 ms log a console warning; copy
  may be unreadable.
- **No title and no description** — renders empty content; always provide at
  least one.
- **Toast before manager mount** — `toast()` lazily creates the manager portal
  with a 10 ms initialization delay.
- **Programmatic dismissal** — `dismissToast(toastId)` using the id returned
  from `toast()`.

## Accessibility

### ARIA roles & attributes

Each toast `<li>` sets:

- `role="alert"`
- `aria-live="assertive"`
- `aria-label` — composite string: `Notification: {status} - {title}. {description}`
- `tabIndex={0}` — toast items are focusable

The manager `<ol>` also sets `role="alert"`, `aria-live="assertive"`, and
`aria-relevant="additions"`. It passes `aria-labelledby` / `aria-describedby`
referencing `toast-title-{id}` and `toast-description-{id}`, but the Toast
component does not currently assign those ids to title and description nodes.

Leading icons use `aria-hidden="true"` when present.

### Keyboard navigation

There is no built-in **Escape** handler to dismiss a toast. Dismissal happens
via timeout, the action button, or `dismissToast(id)`.

### Screen reader behavior

New toasts are announced through assertive live regions on mount. The composite
`aria-label` duplicates title and description — screen readers may read both the
label and visible text depending on browser.

Keep titles short and outcome-first. Do not rely on icon semantics alone.

Action buttons use `aria-label={`Dismiss ${title || "toast"}`}` even for Undo
actions — the visible `buttonLabel` may differ from what assistive tech announces.

### Focus management

Toasts do not trap focus. Focus is not moved to a toast on show. When a toast
dismisses, focus is not restored automatically.

### WCAG criteria

- **1.4.3 Contrast (Minimum)** — strong status backgrounds use onstrong text
  tokens.
- **2.1.1 Keyboard** — action buttons are keyboard-operable; there is no
  keyboard dismiss shortcut today.
- **4.1.2 Name, Role, Value** — role and live region set automatically; name
  comes from `aria-label` and visible title/description.
- **4.1.3 Status Messages** — assertive live regions announce new toasts when
  they enter the stack.

#### Implementation gaps

- **Assertive for all statuses** — `default` and `positive` toasts use
  `role="alert"` and `aria-live="assertive"`, not `role="status"` / polite regions
  as some patterns recommend for success feedback.
- **Broken labelledby wiring** — `ToastManager` sets `aria-labelledby` and
  `aria-describedby` ids that `Toast` does not attach to title and description
  elements.
- **No Escape to dismiss** — keyboard users cannot close a toast with Escape;
  only timeout, action, or programmatic dismissal work.
- **Misleading action aria-label** — action buttons announce "Dismiss" even when
  the visible label is "Undo".
- **`positive` unused in product** — API supports `positive` but teams standardize
  on `default` for success.

#### Design or API debt

- **Title-only stack spacing** — toasts without `description` leave extra gap in
  the stacked layout ([KAI-282](https://linear.app/bsport/issue/KAI-282/toast-update-unfold-animation)).
- **No size variants** — single density only; no `sm` / `lg` prop despite early
  sizing exploration in Linear.
