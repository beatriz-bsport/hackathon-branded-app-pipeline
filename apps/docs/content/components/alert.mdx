## Overview

Alert is a persistent inline banner that surfaces important feedback, system
events, or contextual warnings while the user remains on the page. It stays in
the layout until you remove it or the user dismisses it — unlike
[Toast](/components/toast), which is transient and viewport-fixed. Use Alert
when the message should stay visible, may need an action, or blocks part of the
workflow until acknowledged.

### Use cases

- **Platform-wide block** — global outage, scheduled maintenance, or account
  suspension across the product (`type="strong"` only; see Guidelines).
- **Page-level warning** — flag missing payout configuration at the top of a
  finance view before the user exports data (`type="weak"`).
- **Persistent success** — replace a syncing banner with a success state the user
  should re-read before leaving (e.g. "Billing switches to the new plan on 1
  April"), not a momentary "settings synced" acknowledgment.
- **Blocking error** — surface a payment or integration failure with a Retry
  action while the rest of the page stays read-only.
- **Contextual info** — explain a feature limitation or read-only mode inline
  above the affected form section.
- **Inline callout** — use `layout="inline"` for a compact warning beside a
  specific field group or card.

For lightweight post-action feedback that auto-dismisses, prefer
[Toast](/components/toast). See [Confirmation](/patterns/confirmation) for when
to choose toast, inline success, or no feedback at all.

### Alert vs Toast for success

Brief success when the outcome is off-screen or not obvious — e.g. a settings
sync completed but updated values live on another tab — belongs in
[Toast](/components/toast), not Alert. Toast auto-dismisses and keeps momentum;
the user does not need the message to stay in the layout.

Use a **positive** Alert only when success must **persist** in the page:

- You are replacing an in-progress or syncing **banner** with a success banner on
  the same slot.
- The message includes **follow-up detail** the user should re-read (effective
  date, scope of change, what happens next).
- Dismissal should be **explicit** (`onClearClick`) because the state matters
  until the user acknowledges it.

| Situation                                                    | Pattern                    |
| ------------------------------------------------------------ | -------------------------- |
| Settings synced; user can keep working                       | [Toast](/components/toast) |
| Sync finished; user must note an effective date or next step | Alert (`positive`)         |
| Save visible immediately in the UI                           | No confirmation            |

## Guidelines

- **Match severity to status** — reserve `critical` and `warning` for messages
  that need real attention; use `default` or `info` for routine context.
- **Persistent by design** — Alert does not auto-dismiss; remove it when the
  underlying issue is resolved or the user dismisses it.
- **One message per alert** — keep each instance focused; consolidate related
  points instead of stacking many banners.
- **Pair action with intent** — show `buttonLabel` only when a clear next step
  exists; use `onClearClick` when dismissal alone is enough.
- **Pick layout for context** — `banner` spans the content width; `inline` fits
  the message for contextual callouts.
- **Weak by default** — use `type="weak"` for page- and section-level alerts.
  Reserve `type="strong"` for messages that block the **whole platform** (e.g.
  global outage, maintenance, account suspended across the product).

### Content rules

Keep titles short and scannable; put detail in the body. Write in second person,
present tense, and avoid technical jargon unless the audience expects it.

**Informational (no action)**

> Your account is in read-only mode. Contact your admin to restore edit access.

**Success with dismiss**

> Changes saved. Your payout settings have been updated.

**Warning with action**

> PayPal is not included in this payout. Review PayPal settings to include it in the next export.

**Critical with retry**

> Payment processing failed. Check billing details and try again.

### Behaviors

#### Dismissal

Alerts are persistent — they do not auto-dismiss. Provide `onClearClick` to
render a dismiss control; without it, the banner stays until you unmount it or
navigate away. For transient feedback, use [Toast](/components/toast).

#### Action button

When `buttonLabel` is set, a small default Button appears in the trailing
actions area. Clicking it fires `onButtonClick` only — it does not dismiss the
alert unless your handler removes it.

#### Persistence

Alerts survive re-renders and remain in the document until removed. They are not
queued or stacked by Kaizen — product code owns placement and count.

#### Responsiveness

The banner uses a horizontal flex row (icon, content, actions). On narrow
viewports, long action labels can crowd the trailing area — keep button copy
short or plan for a column layout (tracked in Linear).

### Edge cases

- **Long body text** — string `children` wrap inside the container. Prefer under
  four lines; longer copy may belong in a [Modal](/components/modal) or
  [Panel](/components/panel).
- **Title only** — valid; `aria-labelledby` still targets the title.
- **Body only** — valid when `title` is omitted; no `aria-labelledby` is set.
- **Custom `children` nodes** — non-string children skip automatic `Body`
  styling; you own typography and color.
- **Multiple instances** — stack vertically with layout spacing; avoid more than
  two simultaneous banners on one view.

## Accessibility

### ARIA roles & attributes

The root element is a `<div>` with:

- `role="alert"` — set on every Alert regardless of `status`.
- `aria-live="assertive"` — announcements interrupt immediately.
- `aria-labelledby` — set when `title` or `titleSuffix` is present; points at
  the title element id only (suffix content is not included).

Kaizen does not expose a prop to downgrade live-region politeness for low-severity
messages.

### Keyboard navigation

The alert container itself is not focusable — only trailing Buttons participate
in the tab order.

### Screen reader behavior

On mount, assertive live regions announce the alert. Screen readers typically
read the labelled title and visible body text in document order. The status icon
is decorative in practice — do not rely on icon shape alone to convey severity.

Provide a `title` or body copy that states the outcome explicitly (e.g.
"Payment failed" not only "Error").

### Focus management

Alert does not move focus on mount and does not trap focus. When the user
dismisses via `onClearClick`, focus is not restored automatically — return focus
to a logical control (e.g. the field that triggered the error) in product code.

### WCAG criteria

- **1.4.3 Contrast (Minimum)** — token pairings for `type` and `status` meet
  design-system contrast targets.
- **1.4.1 Use of Color** — pair status colors with explicit title or body text.
- **2.1.1 Keyboard** — action and dismiss controls are operable via keyboard
  when rendered as Buttons.
- **4.1.2 Name, Role, Value** — role and live region are set automatically;
  name comes from `title` and body content.
- **4.1.3 Status Messages** — `role="alert"` and `aria-live="assertive"` expose
  new messages to assistive tech on mount.

#### Implementation gaps

- **Assertive for all severities** — every Alert uses `role="alert"` and
  `aria-live="assertive"`, including `default` and `info`. Low-priority messages
  may interrupt more aggressively than guidelines suggest.
- **Icon cannot be hidden** — there is no prop to omit the leading icon; only
  `customIcon` overrides the default.
- **`titleSuffix` outside accessible name** — supplementary nodes beside the
  title are not referenced by `aria-labelledby`.
- **No focus management on dismiss** — removing an alert does not move focus;
  consumers must handle focus return for keyboard users.

#### Design or API debt

- **Strong scoped to platform blocks** — product convention limits `type="strong"` to whole-platform interrupts; the API still accepts `strong` on any alert. [KAI-680](https://linear.app/bsport/issue/KAI-680/deprecate-strong-variant) tracks whether to remove the variant entirely.
