## Overview

Chip is a compact pill that names a discrete value — a tag, category, or object
status. It carries semantic meaning through color and optional icons, and can be
dismissed when the user removes a tag or other removable selection. Unlike
[Badge](/components/badge), Chip stands on its own as the token itself, not as
side metadata beside another label. For building or displaying list query
filters (field, operator, values), use **Filter** — not Chip.

Not sure whether Chip, Badge, or Indicator fits? See
[Chip vs Badge vs Indicator](/patterns/chip-vs-badge-vs-indicator).

### Use cases

- **Object status** — surface order, invoice, or booking state in a table cell
  (e.g. "Paid", "Cancelled", "Open").
- **Tags and categories** — display member tags, activity types, or segment
  rules with user-defined colors via `customColor`.
- **Removable selections** — show a chosen tag, weekday, or rule the user can
  clear with `dismissible` inside a form (e.g. referral tag picker, recurrence
  weekdays).
- **Session metadata** — group contextual chips such as activity name and
  "Recurring" beside session details.
- **Multi-select toggles** — wrap chips in a `<button>` when the whole pill
  should toggle a value (e.g. enabling a partnership aggregator on a session).

## Guidelines

- **Semantic token** — Chip names the value itself; use
  [Badge](/components/badge) when the pill only qualifies adjacent content.
- **Not for list filtering** — use **Filter** to compose query constraints on
  tables and lists; Chip does not replace field/operator/value filter UI.
- **Dismiss when removable** — set `dismissible` and handle `onClick` when the
  user can remove a tag or other selection from a form.
- **Group related chips** — lay chips in a flex row with consistent `gap`; use
  `ChipList` when a collection may overflow.
- **Match color to meaning** — reserve status colors (`positive`, `warning`,
  `critical`, `info`) for states; use `default` or `main` for neutral tags.
- **Pick density** — `size="sm"` in dense tables and forms; `size="lg"` as the
  default in page headers and detail panels.

### Content rules

Keep labels short, specific, and in sentence case. Name the value or state
directly — avoid prefixes like "Status:" when the surrounding table column
already provides context.

**Status in a table** — `type="weak"`, status `color`, `size="lg"`.

### Behaviors

#### Dismissal

When `dismissible={true}`, a trailing `x` icon appears. Clicking it sets internal
dismissed state, unmounts the chip, and calls `onClick`. Dismissal is optional —
static status chips omit `dismissible` and stay in the layout.

#### Action button

Chip has no primary action slot. `onClick` is dismiss-only and requires
`dismissible={true}`. For whole-chip interactions (toggle, navigate, open menu),
wrap the chip in a `<button>` or link and keep `dismissible` separate.

#### Persistence

The component tracks dismissal internally. Once dismissed, it returns `null` until
remounted. Parent views should own tag/selection state and remove items from
their data model when `onClick` fires.

#### Responsiveness

Chips flow inline and wrap naturally inside flex containers. Long labels expand
the pill width; prefer shorter copy or truncation at the layout level in narrow
columns.

### Edge cases

#### Empty or missing label

When `label` is omitted, the chip still renders if an `iconLeft` or dismiss
control is present; otherwise you get an empty pill — always pass `label` for
text tokens.

#### Invalid customColor

Non-hex `customColor` values are ignored silently; the chip falls back to token
colors from `type` and `color`.

#### onClick without dismissible

`onClick` is ignored when `dismissible={false}` and a console warning is emitted
in development.

#### Multiple instances

Stack chips in a flex row with gap tokens, or use `ChipList` to cap visible chips
and surface overflow in a popover.

## Accessibility

### ARIA roles & attributes

The root element is a non-interactive `<div>` with `data-component="Kaizen-Chip"`.
Kaizen does not set `role`, `aria-live`, or accessible names automatically.

- **Label text** — visible `label` content is exposed as static text in document
  order.
- **Dismiss control** — the dismiss icon is a clickable `<svg>` without a native
  button role or default `aria-label`; consumers must provide context or wrap
  dismissible chips in a labeled group.
- **Interactive wrappers** — when the whole chip is toggled via a parent
  `<button>`, the button owns the accessible name and keyboard behavior.

The built-in dismiss icon is pointer-only today — it is not keyboard-focusable
and has no `Enter` / `Space` handler. Treat this as a known gap when shipping
dismissible tag pickers; consider managing removal from a labeled parent control
until the dismiss affordance is a proper button.

### Screen reader behavior

Screen readers announce `label` text as static content in reading order. The chip
is not a live region — do not use it to announce dynamic system messages; use
[Toast](/components/toast) or [Alert](/components/alert) instead.

For dismissible chips, announce removal by updating the surrounding form or
selection summary so the change is perceptible without relying on the chip alone.

### Focus management

Chip does not trap or move focus. Dismissal unmounts the chip without restoring
focus — parent views should move focus to the next logical control (e.g. the
tag search field) when removing the last selected tag.

### WCAG criteria

- **1.4.3 Contrast (Minimum)** — token pairings use design-system surfaces;
  `customColor` runs through contrast derivation targeting WCAG AA (4.5:1) on
  the tinted background.
- **1.4.1 Use of Color** — pair status colors with explicit label text; do not
  rely on hue alone in tables.
- **2.1.1 Keyboard** — default chip is not operable by keyboard; interactive
  patterns must use a focusable wrapper or an improved dismiss control.
- **4.1.2 Name, Role, Value** — name comes from visible `label` or the parent
  interactive wrapper; dismiss control lacks a dedicated accessible name today.
- **4.1.3 Status Messages** — not applicable for static chips; dynamic outcomes
  belong in Toast or Alert.

### Known issues

#### Implementation gaps

- **Dismiss control is not a button** — the `x` icon uses `onClick` on an SVG
  with no `aria-label`, `role="button"`, or keyboard handlers. Docs recommend
  dismissible selections, but keyboard-only users cannot operate the built-in
  dismiss affordance.
- **`onClick` is dismiss-only** — the prop fires on dismiss, not on whole-chip
  click; toggle patterns require wrapping the chip in a `<button>` (see session
  partnership chips in Studio Manager).
- **Internal dismiss state** — the chip unmounts itself on dismiss; parents must
  sync external state in `onClick` because there is no controlled `open` prop.
- **Invalid customColor fails silently** — bad hex values fall back to token
  colors without surfacing an error to the consumer.

#### Design or API debt

- **No hover or pressed styles** — unlike some legacy chip patterns, the Kaizen
  primitive has no hover feedback; interactive affordance must come from a
  wrapper or dismiss icon cursor.
- **No `md` size** — only `sm` and `lg` exist; some older docs reference a
  middle density that is not in the API.
