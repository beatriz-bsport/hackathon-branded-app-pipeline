## Overview

Tabs navigate between URLs — they are not an in-place view switcher. Use SegmentedControl for that.

Tabs group related pages under a single header so the user can move between them without losing the context they share. In Kaizen, each tab is rendered as an anchor (`<a>`) and _always navigates to a different URL_.

Tabs are a route-level navigation pattern, not an in-place view switcher. If you need to toggle between views _without_ changing the URL (e.g. _Tagged / Untagged_ inside a drawer, _List / Grid_ on the same screen), use _Segmented control_ or _Display_ options instead.

The active tab is visually emphasized so the user always knows which page they are on. Tabs work horizontally (the default) or vertically, can carry an optional leading icon, and support a disabled state.

### Use cases

- _Sub-section navigation:_ Move between related sub-pages within a feature — e.g. _Overview / Members / Billing / Settings_ on a workspace page.
- _Scoped filters as routes:_ Switch between predefined slices of the same list when each slice has its own URL — e.g. _All / Archived_ bookings.
- _Object detail navigation:_ Move between sibling pages of a single object — e.g. _Profile / Bookings / Notes_ on a client page.

### Best practices

#### General

  <Do

  <Dont
    caption={
      "Don't mix unrelated content under one tab set. If the tabs don't share a common subject or page identity, they belong in separate routes or in a different navigation pattern."

<Callout type="warning" title="Caution">

- Limit the number of tabs. Aim for 2–6 tabs. Beyond that, the set becomes hard to scan and likely wraps or scrolls; consider a different navigation pattern (sidebar, filter, dropdown).
- Avoid disabling tabs without explanation. A disabled tab tells the user a section exists but they can't access it; pair it with a tooltip or supporting copy explaining why, or hide it entirely.

</Callout>

### Behavior

_Navigation:_ Each tab is an `<a>` element. Clicking a tab navigates to its `href` using the specified `target` (default `_self`). This means tabs participate in browser history — back/forward works as expected.

_Selection:_ The active tab is determined by `value` (controlled) or `defaultValue` (uncontrolled). `onValueChange` fires when the user picks a different tab, allowing the host to sync state with the router.

_Disabled state:_ A tab with `disabled: true` is not focusable, not clickable, and visually dimmed.

_Orientation:_ `horizontal` (default) lays tabs left-to-right with the indicator below; `vertical` lays them top-to-bottom with the indicator on the inline-start edge.

_Persistence:_ Active tab persistence follows the URL — because tabs are anchors, the active state is naturally tied to the current route.

### Edge cases

_Single tab:_ Don't render a Tabs component with only one tab — remove the navigation entirely and just show the content.

_Tab matching no current route:_ When the URL doesn't match any tab's `href`, fall back to `defaultValue` or leave no tab visually active rather than guessing.

_Overflowing tabs (horizontal):_ When the tab list is wider than its container, use dropdown menu.

_All tabs disabled:_ Avoid this state — if every tab is disabled, the feature is effectively unavailable and should be replaced by an empty/locked state at the page level.

_Icon-only tab:_ Not supported by default — always pair an icon with a visible label. If space is the constraint, switch orientation or pattern.
